# 流式调用治理优化记录

## 背景

当前同步调用和异步任务调用已复用 `AgentCallGuard`，通过 agent 粒度熔断器保护下游 A2A `message/send` 调用。

流式调用当前链路为：

```text
GatewayHandler.invokeStream -> A2AInvoker.Stream -> 下游 Agent message/stream -> io.Copy 转发 SSE
```

该链路暂未纳入公共熔断器保护。

## 问题

流式调用不能直接照搬同步调用的熔断方式。`A2AInvoker.Stream` 内部会通过 `io.Copy(w, resp.Body)` 持续转发下游 SSE 数据，如果把整个流式调用包进熔断器，会带来两个问题：

1. 长连接会长期占用熔断器执行窗口，尤其影响半开状态下的探测请求名额。
2. 熔断统计语义不清晰，客户端主动断开、下游中途失败、正常长流结束需要区别处理。

## 后续优化方向

建议将流式治理拆为两个阶段：

### 阶段一：保护建连阶段

将 `A2AInvoker.Stream` 拆分为建连和转发两个步骤：

```text
OpenStream: 构造请求、发起下游连接、检查 HTTP 状态码
CopyStream: 将下游 resp.Body 通过 SSE 转发给客户端
```

熔断器只包裹 `OpenStream`，将下游连接失败、HTTP 5xx、JSON-RPC 建连错误纳入熔断统计。连接建立后的持续数据转发不进入熔断器统计。

### 阶段二：补充流式专属治理

后续可增加：

- 首包超时，避免下游建连成功但长时间无数据。
- 最大流式连接数，避免长连接占满资源。
- 客户端断开检测，及时释放下游连接。
- 最大流持续时间，避免异常长流。
- 错误分类，区分 upstream error、client cancel 和 normal close。

## 面试表述

同步和异步调用生命周期较短，适合直接纳入熔断统计；流式调用是长连接，如果把整个 `io.Copy` 包进熔断器，会污染统计并影响半开恢复。因此更合理的方案是只对建连阶段做熔断保护，连接建立后的传输阶段通过超时、连接数限制和断开检测治理。
